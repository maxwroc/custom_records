## Plan: SQLite Storage and Aggregation

Adopt SQLite before the first release, while there is no installed-user migration burden. Use one integration-owned database with a native `STRICT` table per record type, explicit logical-to-physical identifier metadata, immutable schemas with optional-field additions, indexed integer timestamps, transactional writes, a stable structured aggregation API, and a separately isolated bounded read-only SQL API for advanced cards. SQLite is preferred over JSON Store because automation writes need incremental durability, record volume is uncertain, and direct SQL access is now a product requirement. Aggregation alone would not justify this migration.

**Implementation status**
- Done: Phase 1 schema contract and DDL-first additive updates, including physical schema validation and a persistent Repairs issue when configured tables are missing/mismatched; Phase 2 SQLite storage with serialized transactions, commit-failure rollback, and coordinated media writes/cleanup; Phase 3 backup hooks that pause operations and close/reopen/validate the database; Phase 4 `custom_records/aggregate_records` WebSocket command, including `filter`; and the immutability parts of Phase 6 (config flow: removed `change_field_key`/`delete_field`/`change_type_key`, blocked adding a required field to an existing type, and preserved immutable physical mappings during edits; storage/filter/aggregation/backup tests rewritten; README updated).
- Done: select-option list is now fully editable via the `edit_select_options` config-flow step (add/remove/rename/reorder), superseding the earlier append-only `append_select_option`. Only forward writes are validated against the current options; stored records are never rewritten, so removed/renamed values remain as orphaned historical values that still read/export. A field default that references a value no longer in the list is auto-pruned (cleared for single-select, missing items dropped for multi-select).
- Deliberately deferred (tracked as future work, not started): Phase 5 (the bounded read-only raw-SQL `custom_records/query` API + authorizer), separately gated so storage delivery is not blocked on it - see the **Decisions** section's final bullet.
- Also not implemented this pass: `PRAGMA quick_check`/broader corruption classification and the full adversarial/disk-full/orphan-schema test matrix from Phase 6 pt.32/35.
- Done: unified `list_records` storage reads return `RecordsPage` with explicit ascending/descending order independent of limit. Unlimited internal reads have no continuation; public requests default/cap at 500 records and support both directions with order-bound cursors. Removed prerelease capability discovery and API/pagination versioning; runtime-local handles retain 30-minute idle expiry and live-read semantics.

**Steps**

### Phase 1: Lock the storage and schema contract
1. Treat this file as the sole implementation plan. The project is unreleased and has no installed-user data migration obligation; the obsolete JSON-first plan has been removed rather than retaining contradictory decisions.
2. Define one database at a stable integration-owned path under Home Assistant's backed-up config storage. The manifest's `single_config_entry: true` invariant means one database can safely contain all record types and support cross-type SQL. Keep one native table per record type. Home Assistant config subentries remain the authoritative registry of configured record types and semantic metadata; never infer configured types merely by listing SQLite tables.
3. Persist a separate physical `sql_table` name on each record type and `sql_column` name on each field alongside the logical `id`/`key` in config-subentry data. Initially generate deterministic names such as `records_<record_type_id>` and `<field_key>`, so logical and physical field names will normally match, but treat both values as explicit immutable metadata. This preserves an unambiguous public mapping and leaves room for collision handling or a future deliberate logical-key alias without silently changing an existing SQL schema.
	- Validate logical record-type IDs and field keys against the product's restricted identifier pattern, reserved public/internal names, and length limits before generating physical names.
	- Validate generated physical names for uniqueness within their scope and reserve SQLite/internal integration prefixes and names.
	- Centralize SQL identifier double-quoting for every generated statement; identifier validation does not replace quoting. Never interpolate record values.
4. Make every record table `STRICT` (the supported HA runtime exceeds SQLite 3.37). Define exact storage contracts:
	- `id TEXT PRIMARY KEY NOT NULL`; generate UUIDs internally, but accept imported IDs as bounded non-empty opaque text after rejecting control characters.
	- `timestamp INTEGER NOT NULL`, storing signed Unix microseconds in UTC. Require offset-aware API/import timestamps and `datetime` field values; reject naive values rather than silently applying the HA local timezone. Convert with integer/timedelta arithmetic rather than a floating-point `datetime.timestamp()` round trip, including before 1970. Use integer arithmetic for equality/ranges and divide explicitly when SQLite calendar functions or ApexCharts milliseconds are needed.
	- Required user fields are `NOT NULL`; optional user fields are nullable. Define one authoritative default policy before implementation: validate/default values in the domain layer and always bind every supplied/defaulted column explicitly, rather than relying on SQLite defaults for normal writes. Existing rows created before an optional field was added remain `NULL`; no `ALTER TABLE` backfill occurs in P0. Validate every configured default against its field type/options when a record type is created or loaded, persist its canonical storage representation in metadata, and prohibit SQL column `DEFAULT` clauses unless a later migration deliberately makes them part of the public contract.
	- Number fields use `REAL`; reject `NaN`, positive infinity, and negative infinity before persistence or aggregation.
	- Boolean fields use `INTEGER CHECK (<column> IN (0, 1))`.
	- Datetime fields use UTC Unix microseconds in `INTEGER`, normalized from offset-aware input.
	- Text, long text, and single-select fields use `TEXT`, with explicit request/import size limits.
	- Multi-select uses canonical compact JSON-array `TEXT`; preserve item order and reject malformed/non-array JSON on decode. JSON1 is required because `list_records` and `aggregate_records` support membership filters; confirm it in the minimum supported HA runtime, enforce `CHECK (json_valid(<column>) AND json_type(<column>) = 'array')`, and fail setup clearly if unavailable rather than silently weakening filtering or validation.
	- Image fields store only their validated filename in `TEXT`; the public shape exposes a deterministic `media_source` link generated at serialization time (never stored).
5. Create an index on `(timestamp, id)` for every record table. All range lists, exports, retention, and maximum-record operations use `id` as the deterministic tie-breaker when timestamps match. Internal `list_records` callers must specify ascending or descending order explicitly; limit never changes direction. CSV exports and existing media scans explicitly use ascending order. WebSocket listing defaults to descending but supports either direction, including cursor traversal; no caller may rely on SQLite's unspecified natural row order. Do not expose user-managed indexes in P0; add more only from measured query patterns.
6. Make record-type IDs, field keys/types/requiredness/defaults, `sql_table`, and `sql_column` immutable after creation. Keep labels, units, retention, limits, and warning settings editable. Select `options` are fully editable (add/remove/rename/reorder) via the `edit_select_options` step because only forward writes are validated against them and stored records are never rewritten: a removed or renamed value survives as an orphaned historical value that still reads/exports, and a field default that no longer matches the list is auto-pruned. Allow only optional fields through `ALTER TABLE ADD COLUMN` in P0; required-field additions need an explicit future data-migration workflow. The config flow's existing-type "add field" step must therefore reject `required=True` outright (only the create-new-type wizard may collect a required field), and an "edit select options" step is provided for existing `single_select`/`multi_select` fields. Remove field deletion, field-key/type change, and record-type-key rename flows. Whole-type deletion remains supported after confirmation.
7. Config subentry persistence and SQLite DDL cannot commit atomically, so use an explicit idempotent operation protocol:
	- Initial bootstrap is identified by a newly created empty database/version and creates every configured table before setup completes.
	- New record type: generate and validate immutable mappings, create the table transactionally, then publish the subentry. If metadata publication fails, the table remains an orphan for a safe retry or explicit cleanup.
	- Add field: add and validate the optional column transactionally, then publish the updated field metadata. A retry may adopt the column only when its exact name, type, nullability, and constraints match the pending field.
	- Delete record type: remove the subentry first, then drain operations and drop the now-orphaned mapped table and media. A crash leaves preserved orphaned data rather than metadata pointing to missing data.
	- Never silently recreate a missing table in an existing initialized database. Treat a configured type with a missing/mismatched table as possible data loss: fail that entry's setup safely and raise a Repairs issue.
	- Preserve and hide tables/columns with no authoritative metadata. Report them as orphans; do not automatically expose, delete, or adopt them outside the exact retry cases above.
8. Do not add custom record-type/field registry tables in P0; they would duplicate config-subentry metadata and create competing authorities. Validate physical state using `PRAGMA table_list`, `table_xinfo`, `index_list`/`index_info`, and constrained `sqlite_schema` inspection so checks cover `STRICT`, columns, constraints, and required indexes. Never rewrite mismatched schema automatically.
9. Track integration database format with `PRAGMA user_version`. Reject a database with a newer unknown version. Run each future version migration in an explicit transaction where SQLite permits it, update `user_version` only after success, and test rollback/retry after interruption.

### Phase 2: Build an asynchronous database boundary
10. Replace `/workspaces/custom_records/custom_components/custom_records/store.py`'s in-memory lists and HA `Store` files with a database-backed `RecordStorage` interface while preserving domain methods so callers do not execute SQL directly.
11. Use Python's standard `sqlite3` with explicit transaction configuration, not version-dependent defaults. Create and use the primary connection on one dedicated single-worker executor; keep `check_same_thread=True`, never use that connection from arbitrary HA executor threads, and explicitly commit, roll back, and close it on its owning worker. A third-party async wrapper is unnecessary unless implementation evidence disproves this model.
12. Commit each single-record mutation transactionally. Bulk import, retention deletion, maximum-record enforcement, and schema changes each use explicit transactions. Queue application operations through the serialized worker. Fire update events only after commit; a rollback must produce no success response or update event.
13. Start with rollback-journal mode and a documented `synchronous` durability setting. The checked development runtime is SQLite 3.46.1, which predates the WAL-reset fix in 3.51.3 and selected backports; rollback mode also simplifies HA backups. Reconsider WAL only after runtime-version gating and measured lock contention justify it.
14. Convert every storage read to a truly async method and update integration setup/removal/purge, WebSocket handlers, services, config flow, CSV export, media browsing/resolution/cleanup, and Repairs counts. Do not load all records at setup. Paginate/stream internal scans such as media-reference cleanup and CSV export instead of materializing an unbounded table. Rework `filter_query.py`'s compiled per-field comparison predicate (used today by `custom_records/list_records`) into a compiler that emits parameterized SQL `WHERE` clauses over validated mapped columns instead of a Python callable applied after the fact; reuse the same compiler for the aggregation API's `filter` parameter (Phase 4). Preserve current missing-value semantics exactly: every ordinary comparison, including `!=`, requires the column to be non-NULL; multi-select equality/inequality uses JSON1 membership but must also require a non-NULL column, so a missing optional multi-select field matches neither `==` nor `!=`. Never fetch an unbounded/timestamp-range-only row set into Python and filter it there merely to keep this predicate logic unchanged.
15. Preserve export/import behavior with deterministic `ORDER BY timestamp, id`. Import validates bounded CSV input, then runs one serialized transaction:
	- Route each parsed CSV row through the same domain-level field normalization as service/WebSocket writes, so requiredness, type validation, canonical encodings, and configured optional defaults are applied identically before deduplication and insertion. Reject naive imported record timestamps and `datetime` field values under the common UTC contract.
	- Duplicate primary IDs are skipped and never overwrite existing rows.
	- Content duplicates compare the exact canonical tuple of timestamp plus every logical field, including nulls and canonical multi-select/image representations. Query candidates by timestamp and compare canonical rows in Python unless benchmarks justify an internal fingerprint; do not rely on a collision-prone hash alone.
	- Maintain an in-batch signature set. Rows supplied without timestamps receive UTC timestamps but intentionally remain exempt from content deduplication, preserving current behavior.
	- Apply retention/max-record policy after the batch in the same transaction so a large import cannot leave the table above its configured limit.
16. Implement retention with `timestamp < cutoff`. Enforce maximum records by deleting exactly the rows after the newest configured limit under `ORDER BY timestamp DESC, id DESC`; define these tie-break semantics in tests. Use `COUNT(*)` for warnings.
17. Coordinate image files with transactions: copy an image before inserting its row, delete the copied file if the insert fails when possible, and rely on startup cleanup for crash leftovers. Stage each newly copied file outside the live media tree (or reserve it through the shared operation gate) until its insert has committed, so a simultaneous post-commit orphan cleanup cannot delete a file between copying it and recording its reference. Promote/reserve the file and insert its row under one serialized media/storage protocol; if promotion or insertion fails, remove the staged/live copy when possible. Delete record rows first and clean now-unreferenced media only after commit. Never delete a potentially referenced file inside a transaction that can roll back.
18. Ensure unload rejects new work, interrupts/drains bounded query work, drains application operations, commits or rolls back, and closes all connections/executors. Integration removal closes first, then removes the database and media. Make repeated close/remove calls idempotent.

### Phase 3: Backup and failure behavior
19. Add Home Assistant `backup.py` `async_pre_backup`/`async_post_backup` hooks. A shared operation gate rejects or waits for new work with a bounded timeout, interrupts active advanced queries, drains primary operations, commits, and closes every DB connection before backup. `async_post_backup` reopens and validates the database and releases waiters; cleanup must run in `finally`-equivalent paths so failed backup creation cannot leave the integration permanently paused.
20. Treat SQLite as transactional infrastructure, not infallible storage. Configure a bounded busy timeout, distinguish lock/time-limit errors from corruption, roll back failures, log safely without record values, and raise Repairs issues. Fail setup without overwriting, deleting, or auto-recreating a malformed/mismatched database. Use `PRAGMA quick_check` after a failing/unclean open and during backup-restore verification, not on every normal startup.
21. Handle disk-full/read-only/I/O failures explicitly. A failed write leaves prior data intact and returns an error; maintenance jobs report failure without disabling future retries. Do not run routine `VACUUM`; consider an explicit maintenance action only when measured free-page growth warrants the temporary disk and exclusive-operation cost.

### Phase 4: Structured aggregation API
22. Add `custom_records/aggregate_records` with required `record_type`, `op`, and `bucket`; optional inclusive `start`/`end`; required numeric `field` for `sum`/`avg`/`min`/`max`; field forbidden for record `count`; optional `format` defaulting to table buckets; and an optional `filter`, accepting the same AND-combined per-field-key comparison shape as `custom_records/list_records` (see `filter_query.py`). Compile `filter` with the same validated-column SQL `WHERE` translation used for `list_records` (Phase 2 point 14) and apply it before bucketing/aggregating, so aggregation results only ever cover a filtered subset when requested and never require pulling unfiltered rows into Python first. Normalize range inputs to UTC microseconds and reject naive/invalid datetimes or `start > end`.
23. Define calendar buckets in UTC: UTC day, ISO-style Monday week, and UTC calendar month. Rolling seven-day windows are not calendar weeks. Document inclusive range endpoints and bucket-start labels precisely.
24. Execute aggregation over validated mapped identifiers, applying the compiled `filter` (if given) with the same field-type/operator validation `list_records` enforces (unknown field, unsupported field/operator, and invalid-value errors must match). Return sparse ascending buckets only. Omit periods with no rows; for numeric operations also omit a bucket with no non-null selected values. Numeric bucket `count` is the number of values aggregated; standalone count counts records. Verify large finite sums: SQLite may return infinity even when inputs were finite, so reject non-finite aggregate results with a clear API error rather than emitting invalid JSON.
25. Return either `{"buckets": [{"start": <UTC ISO>, "value": <number>, "count": <integer>]}` or ApexCharts-ready `{"series": [{"name": <field label or Count>, "data": [{"x": <epoch milliseconds>, "y": <number>}]}]}`. Keep this structured API stable so ordinary cards are insulated from physical schema details.

### Phase 5: Bounded read-only SQL API
26. Implement the advanced `custom_records/query` command only after storage and structured aggregation are stable. Keep the accepted all-authenticated-users policy and document that every authenticated HA user can query every custom-records table; configuration remains admin-only, but dashboard cards run with viewer credentials.
27. Never run advanced SQL on the primary application worker. Use a separate bounded executor with a strict concurrency/queue limit and one short-lived read-only URI connection (`mode=ro`) per active query. Backup/unload can interrupt these connections without compromising the primary connection. Rollback-journal readers may still delay writes, so deadlines must bound lock duration.
28. Pass the submitted text to `Connection.execute`, which enforces one statement, and use an authorizer allowlist rather than trusting a `SELECT`/`WITH` prefix. Allow read-only SELECT/CTE operations over approved `main` tables and deterministic built-in functions. Deny writes, DDL, transaction control, `ATTACH`/`DETACH`, virtual-table creation, extension loading, dangerous PRAGMAs/functions, temp schema access, and reads from undeclared/orphan/internal objects. Disable extension loading and set SQLite runtime limits for SQL length, expression depth, compound selects, columns, and attached databases where available.
29. Use `set_progress_handler` with monotonic deadline/cancellation state; cap query text size, execution time, concurrent queries, fetched rows, columns, per-cell text/blob size, and final serialized bytes. Fetch incrementally and stop before building an oversized response. Return only JSON-safe null/integer/finite-float/text values; reject blobs, non-finite results, duplicate/empty column names if the response shape cannot represent them safely. Always finalize cursor and close connection.
30. Publish schema discovery sourced from authoritative config metadata after physical validation. Return each record type's logical `id`, display metadata, exact `sql_table`, and fixed base-column contract (`id TEXT PRIMARY KEY NOT NULL`; `timestamp INTEGER NOT NULL`, UTC Unix microseconds); return each field's logical `key`, semantic/display metadata, exact `sql_column`, storage type, nullability, and encoding notes. State that configured defaults are applied by normal integration writes, not by SQLite column defaults, and that pre-addition rows have `NULL` in added optional columns. Logical and physical names remain separate even when equal. For example:
		```json
		{
			"record_types": [{
				"id": "blood_pressure",
				"name": "Blood Pressure",
				"sql_table": "records_blood_pressure",
				"fields": [{
					"key": "systolic",
					"label": "Systolic",
					"type": "number",
					"sql_column": "systolic",
					"sql_type": "REAL",
					"nullable": true,
					"encoding": "finite_number"
				}]
			}]
		}
		```
		State that this SQL schema is an advanced public contract. Future physical changes require compatibility views or a documented breaking release, unlike the structured aggregation API.

**Decisions**
- Revised recommendation: migrate to SQLite before P0-5 and before the first release.
- There are no released installations, so no JSON-to-SQL user-data migration is included. Keep the old implementation only until parity tests/benchmarks pass, then remove it before release.
- Native per-record-type tables are preferred over a whole-record JSON payload. Limited serialization remains only for intrinsically compound values such as multi-select.
- Config subentries, not discovered database tables, are authoritative for configured record types and semantic field metadata. No duplicate custom metadata registry tables are planned for P0; database introspection validates physical state and detects orphans.
- Logical record-type/field identifiers and physical `sql_table`/`sql_column` identifiers are persisted and exposed separately, even when generated with the same value. This makes the exact SQL schema discoverable and avoids assuming that logical names must always equal physical names.
- Schema evolution is additive only; logical IDs/keys, physical SQL identifiers, types, requiredness, and defaults are immutable. Optional fields and select options may be appended.
- SQLite transactions and serialized worker access resolve in-process concurrent-write concerns. The current Store implementation is not known to lose two normal in-process HA writes because both mutate one event-loop-owned in-memory list before the delayed snapshot, but SQLite gives each mutation explicit durable transaction semantics and avoids whole-file rewrites.
- UTC calendar buckets replace the earlier HA-local timezone decision for SQL consistency.
- Keep both APIs: structured aggregation is stable/easy; bounded read-only SQL is advanced/flexible.
- SQL is available to all authenticated users because dashboard cards execute as their viewers, not as the admin who configured the card. It can read all custom-records tables.
- Read-only SQL still requires statement, attachment, runtime, row, and response limits. These protect availability and isolation from mistakes as well as malicious input; they do not restrict normal aggregate/join/CTE card queries.
- Use exact UTC Unix microseconds in `INTEGER` timestamp/datetime columns, reject non-finite numbers, and require `STRICT` tables on the supported runtime.
- Use rollback journal initially. The current development SQLite 3.46.1 predates the relevant WAL-reset fix; WAL is an optimization, not a prerequisite for transactions or safe queued writes.
- Ship the structured aggregation API with storage. Treat the advanced SQL API as a separately gated follow-up within this plan so storage delivery is not blocked if adversarial-query or contention testing finds unresolved risk.
